# TurnLens Roadmap

**Sections:** The name · Plans 1 to 5 · Deferred decisions · Open questions

Each plan produces working, testable software on its own.

A question answered here moves to `DECISIONS.md` rather than being deleted.
Candidate features with evidence behind them live in `FUTURE.md`.

Paths under `docs/superpowers/` name the design document a plan was worked out
in. That directory is scaffolding and is not part of the repository; anything
from it that outlived the work it was written for is already here, in
`ARCHITECTURE.md`, or in `DECISIONS.md`.

## The name

The project was called **TurnScope** until 26 July 2026. It was renamed because
`turnscope` is already published on npm -- two versions, and on a close enough
subject that sharing the name would be actively confusing -- so the name could
never have been the install command. `turnlens` was checked and found free on
npm, crates.io, PyPI, Homebrew, Google Play and GitHub, with `turnlens.dev` and
`turnlens.io` unregistered.

Every document here, including the dated plans and the archived Python phase,
was rewritten to the new name. That means code excerpts and quoted commands in
those records now read `turnlens` where the machine at the time said
`turnscope`. The dates and the reasoning are unchanged; only the name moved.

## Plan 1 — Core and Codex provider (complete)

`docs/superpowers/plans/2026-07-25-turnlens-core-codex-provider.md`

Zero-dependency TypeScript CLI that live-monitors one Codex session and records
per-turn token usage to CSV. It fixes the Python prototype's defects
structurally rather than by patching: the aborted turn leaking into the next
one, the terminal re-spawning and pipe misbehaviour, event names that never
occur, partial lines and undetected file rewrites, accumulating lock files, the
CSV being rewritten on every start, and the absence of tests and of `--help`.

All ten tasks are done: 156 tests passed at the time, `npm run typecheck` and
`npm run build` both exited 0, and `node dist/cli.js` ran end to end. The work
was done on a `feat/ts-core` branch, which no longer exists -- it was merged into
`main` and deleted when the history was rewritten for the public repository. The abort leak is verified twice over — against the committed fixture, and in a live
Codex session where a deliberate Esc interrupt produced a 30,740-token `aborted`
row followed by a separate 24,775-token `completed` row instead of one merged
55,515-token row.

Cost was out of scope for Plan 1: the `estimated_cost_usd` column was written
empty until Plan 2 filled it.

## Plan 2 — Native pricing (complete)

`docs/superpowers/plans/2026-07-25-turnlens-native-pricing.md`

Removes the external `ccusage` dependency, which currently costs up to twelve
subprocess spawns per turn (P2-2).

Shipped: `src/pricing/`, eight modules, 247 tests green. The external `ccusage`
dependency is gone; no subprocess is spawned for pricing at all.

- LiteLLM `model_prices_and_context_window.json` filtered at build time to the
  providers TurnLens monitors: **113 models, 16 KB**, embedded and shipped,
  regenerated by `npm run pricing:snapshot`.
- **LiteLLM is the only source**, behind an interface that admits a second one
  later. `models.dev` is not implemented; every model these providers emit is
  already in LiteLLM under its exact recorded name.
- **Online by default, offline as a mode.** Before monitoring starts — once, never
  during the watch — TurnLens asks LiteLLM whether its price list has changed,
  sending the stored `ETag` as `If-None-Match`. The measured answer for an
  unchanged list is `304` with zero bytes transferred, which is what makes an
  online default affordable on every run. A changed list is downloaded and
  written to `~/.turnlens/pricing/`, which is also what `--offline` prices from,
  so offline mode is fed by ordinary online use rather than by a separate update
  mechanism. Any network failure falls through to that cache and then to the
  embedded snapshot within five seconds, so a watch always starts. An earlier
  revision of this document proposed a TTL-based refresh; the conditional check
  gives the same freshness without choosing an interval.
- **A closed turn is never repriced.** It keeps the rate that was in effect when
  it closed, and the row records which list that was. Unlike ccusage, which
  recomputes history on every invocation, TurnLens writes each row once.
- Handles `cache_creation_input_token_cost` and the `_above_1hr` tier, which is
  what Claude Code's 5m / 1h ephemeral split requires.
- **Long-context tier rates are deliberately unused.** A turn's token total is
  the sum over many requests, not one request's context size, so comparing it
  against the 272,000-token threshold would misprice systematically. Deferred
  below.
- Unknown model resolves to `unavailable`, never `0`. The reason is recorded in a
  `cost_status` column so an empty cell can be explained.
- Every row records the pricing version so historical numbers stay explainable.

Verified against `ccusage codex session --json` as an independent oracle over a
real 45-turn session. **The rates agree exactly**: applying TurnLens's rates to
ccusage's own token counts reproduces ccusage's total to the cent
($37.229909). The remaining 0.62% difference in the totals
($36.997827 against $37.229909) is entirely token attribution, not pricing --
TurnLens counts marginally fewer tokens in all three categories, which is the
known boundary behaviour of recording only turns it can attribute. Also verified
live: a 304 on the second run leaves the cache untouched, `--offline` reports the
same version marked `(offline)`, and an unroutable source falls through in
exactly 5.0 seconds with one notice and correct prices from cache.

## Plan 3 — Claude Code provider (complete)

`docs/superpowers/plans/2026-07-26-turnlens-claude-code-provider.md`

Shipped: `src/providers/claude-code/parser.ts` and `sessions.ts`, plus the
registry entry. **310 tests green**; `npm run typecheck` and `npm run build`
both exit 0. `node dist/cli.js --help` now reads `One of: codex, claude-code`.
**The CSV schema did not change**, so nobody who started recording under Plan 2
has to migrate.

Nothing in `core/`, `pricing/` or `ui/` changed. The adapter layer was designed
for exactly this, so most of Plan 3 was already written and untested rather than
undone: `TurnAssembler` already implemented `usageModel: "per-event"` and the
optional `dedupKey`, and `claude-opus-5` was already in the embedded pricing
snapshot including the one-hour cache-creation tier, which Codex never
exercises.

Three plan defects surfaced during execution and are recorded in the commit
bodies: an event-order assertion that a later task correctly invalidated, a
Plan 1 registry test that used `claude-code` as its example of an unsupported
provider, and a claim that the pipeline test would fail with the replay filter
disabled -- it does not, because the assembler's own guards already absorb a
verbatim replay.

**Live verification found two real defects that no automated check had.** Both
are fixed, both have regression tests, and both are the reason this step is not
optional.

The first is a product defect of the abort-leak class. Claude Code writes two
interruption markers, `[Request interrupted by user]` and
`[Request interrupted by user for tool use]`, and the shipped constant included
the closing bracket of the first, so a turn interrupted mid tool call was never
closed. Its 41,120 tokens and its `WebSearch` call were recorded against the
next prompt, which was "3+3?". Every arithmetic check still passed, because no
token was lost or double counted -- only the attribution was wrong.
`test/fixtures/claude-code-tool-interrupt.jsonl` reproduces it.

The second was in the verification tool itself. `scripts/verify-costs.mjs`
compared with a `< 5e-7` tolerance, which rejects correct rounding: a turn
costing 0.2653995 is stored as 0.265400, off by exactly 5e-7. It reported
MISMATCH while printing two identical-looking numbers, because both were printed
rounded.

Verified live over 16 turns in a session kept aside for testing, per the rule in
`CLAUDE.md`: interruptions during a reply and during a tool call each produce
their own `aborted` row with their own tool call, following prompts are clean,
and `npm run verify:costs` reports 16 of 16 rows `ok`, $1.290848 total.

Scope: **one session file at a time**, matching the Codex provider. Subagent
transcripts live in a separate directory and are deliberately out of scope; see
the deferred decisions below.

- `usageModel: "per-event"` with two distinct deduplications, both mandatory and
  both measured. A compaction re-appends the preserved segment verbatim, so a
  record whose `uuid` was already seen is replayed history and is dropped whole;
  independently, one API response is written as several records, one per content
  block, sharing `message.id` + `requestId`, so usage is counted once per pair.
  Measured on a frozen copy of a real session: 3,702 assistant records reduce to
  730 responses, and turn boundaries fall from a phantom 87 to the true 59.
- Turn boundaries from `promptId` on user records. Assistant records carry no
  `promptId`, so they belong to the prompt they follow. `stop_reason: "end_turn"`
  closes a turn.
- **Correction found during implementation.** The design said `end_turn` appears
  at most once per turn. It does not: a closing response is split across content
  blocks like any other, and every record of it carries `stop_reason:
  "end_turn"`. Measured on the fixture session, all four closing responses are
  written twice under the same `message.id` and `requestId`. The second
  `turnEnd` closes a turn that consumed nothing, which `TurnAssembler` drops, so
  no row is duplicated and no tokens move -- but the assembler dropping empty
  turns is load-bearing here, not merely tidy.
- Interrupted turns are recorded as a user record whose text is
  `[Request interrupted by user]`; compaction as a system record carrying
  `compactMetadata`. Both already have somewhere to go -- `turnAbort` and
  `boundary`.
- Reasoning tokens are **not reported by Anthropic**. `thinking` content blocks
  exist but `message.usage` has no reasoning counter, so the column is 0 for
  Claude Code while Codex fills it. This asymmetry is real and must be
  documented rather than papered over.

Verified before implementation: applying these rules to a frozen copy of the
local sessions reproduces `ccusage claude session --json` exactly -- 14,047
input, 136,323,205 cache read, 3,375,268 cache creation, 718,140 output,
`$118.867966`, with no difference in any figure. Both tools price from LiteLLM,
so the rates were never in question; this establishes that the token attribution
agrees too.

## Plan 3.5 — Pre-release cleanup (complete)

`docs/superpowers/plans/2026-07-27-turnlens-pre-release-cleanup.md`

`src/cli.ts` was the only source module no test imported -- one of 27 before this
plan, 28 after it added `src/options.ts` -- and the reason was structural rather
than neglect: a top-level `await main()`
means importing the file runs the program, listing sessions and blocking on a
prompt. So the guards it applies -- an unknown provider, two contradictory flag
pairs, previews defaulting to off under a pipe, an out-of-range session number --
had never been exercised, and a guard whose only job is to fire on bad input is
worth nothing unchecked.

Those decisions now live in `src/options.ts`, which does nothing at import time.
`argv` and whether a terminal exists are parameters rather than reads of
`process`; without the second, the piped-stdin branch would stay unreachable,
because a test process has no terminal.

**`cli.ts` is still not imported by any test, and that is the intended end
state.** It still ends in `await main()`. What changed is that there is nothing
left in it worth importing: 196 lines became 169, and 14 branch points became 8.
The three `if`s that remain print the help text, print the refresh notice, and
throw when the provider returned no sessions -- the last a one-line guard over an
I/O result, where extraction would buy indirection and no coverage.

329 tests across 26 files, up from 314 across 25.

Done before v0.1.0 deliberately. A published version freezes what it contains,
so a restructure that costs nothing today costs a version number tomorrow.

## Plan 3.6 — Session discovery across platforms and configurations (complete)

`docs/superpowers/specs/2026-07-27-session-discovery-design.md`

Shipped: `src/core/home.ts` and `src/core/env-paths.ts`, plus changes to
`core/paths.ts`, both providers, `core/types.ts`, `options.ts` and `cli.ts`.
**375 tests across 28 files**, up from 329 across 26; `npm run typecheck` and
`npm run build` both exit 0. The packed tarball goes from 31 files to **33**.
No recorded row changes shape or value, so nobody has anything to migrate.

### The Windows run found three more, and that is the point of it

The six defects above were designed against a measurement and a reading of
ccusage. Then TurnLens was cloned onto the Windows machine and actually run --
the first time the program rather than a probe had executed there -- and three
further defects surfaced immediately. Every one had passed a full green suite on
Linux.

- **Deduplication compared spellings, not directories.** `~/a` expands through
  `join` and returns with backslashes while a path the user typed keeps forward
  slashes, so one directory survived as two roots and every session in it would
  have been listed twice. Roots are canonicalised now, and a doubled separator
  gives Linux a way to see the same defect.
- **The session list was wider than the rule it drew.** 106 characters for
  Claude Code and 145 for Codex under a 100-character rule, so any narrower
  terminal wrapped a row -- and a wrapped row reads as corruption, which is
  exactly how it was first reported. The columns add up to the rule now, with 39
  reserved for the id because a uuid is 36 and three more mark a cut.
- **Three assertions carried a Linux separator.** Canonicalising made them fail
  on Windows, where `normalize("/a")` is `\a`. The production behaviour was
  right; the tests were comparing literals where the rest of the suite compares
  `join` results.

Two open questions from that run were also closed, and neither was a defect. An
archived Claude Code conversation keeps appearing in the session list because
nothing on disk marks it -- see `docs/ARCHITECTURE.md`. A Codex session showing
`(unnamed session)` was genuinely absent from `session_index.jsonl`, so reporting
no name was correct.

The design estimated 360 tests. The five extra are edge cases the behaviour lists
implied without naming — a whitespace-only `HOME`, a variable of only commas, two
entries that differ before expansion and agree after it. The estimate was built
by counting listed behaviours, and writing them found more.

Each fix was verified against this machine's real sessions as well as its tests:
the Claude Code defaults still resolve to the same two roots and find the same
eight transcripts, Codex still finds the same twenty, and
`CLAUDE_CONFIG_DIR=/nonexistent turnlens --provider claude-code` now exits 1
naming the root it searched and both variables it consulted.

Where a session file lives is the one thing TurnLens has never verified anywhere
but the machine it was written on. Plan 4 was going to settle that with a CI
matrix, and a CI matrix cannot: the runners have no Codex or Claude Code
installation, so a green Windows job proves the test suite passes, not that
TurnLens can find a transcript. This plan closes the gap before the package
freezes, with the same evidence standard the rest of the project uses.

Two independent sources were used, and neither is inference.

**A Windows machine, measured directly** on 27 July 2026 -- Windows 10, Node
24.18.0, both agents installed, run under PowerShell and Git Bash. Written up in
`docs/ARCHITECTURE.md`, "Validated on Windows". Its headline result is that
**the paths are already right**: `~/.codex/sessions/<y>/<m>/<d>/rollout-*.jsonl`
and `~/.claude/projects/<project>/<session>.jsonl` both hold, line endings are
LF, and the lock is atomic. It also retired a recorded suspicion: the
`resolveTurnlensHome` soft spot does not reproduce, because Git for Windows sets
`HOME` to `%USERPROFILE%`.

**ccusage's own path resolution, read from source.** It supports fifteen agents
on three platforms and has absorbed years of user reports, so what it checks is
evidence about the world rather than a guess about it. `rust/crates/
ccusage-core/src/home.rs`, `rust/adapters/claude/src/paths.rs` and
`rust/adapters/codex/src/paths.rs` are the relevant files.

That reading corrected a conclusion this project was about to draw. The second
Claude Code root is **not** a historical location that could be deleted for lack
of sightings. It is the XDG one: ccusage resolves `XDG_CONFIG_HOME`, defaulting
to `~/.config`, and only then appends `claude`. TurnLens hardcodes
`~/.config/claude` and never reads the variable, so the root is not dead -- our
implementation of it is incomplete. The comment in
`providers/claude-code/sessions.ts` saying both defaults are checked "because
Claude Code has used both over time" states a reason that is not the real one.

### What is wrong, each confirmed in our own source

None of these is a Windows defect. Every one is missing on all three platforms,
which is why the Windows measurement did not find them and a second source was
needed.

| Defect | Where | Evidence |
|---|---|---|
| An empty `HOME` produces a **relative** state directory | `core/paths.ts` | `HOME=""` yields `.turnlens`, not `<home>/.turnlens`, because `??` treats an empty string as a value. Locks and the pricing cache would land in the working directory -- reinstating, silently, the exact defect corrected earlier and described under "Where files go" |
| `XDG_CONFIG_HOME` never read | `providers/claude-code/sessions.ts` | the string does not occur anywhere in `src/` |
| Two different home resolutions in one program | `core/paths.ts` reads `HOME` then `os.homedir()`; both providers call `os.homedir()` alone | sessions read under one home, lock and pricing cache written under another wherever the two disagree |
| `~` not expanded in configured paths | both providers | `CLAUDE_CONFIG_DIR=~/foo` looks for a directory literally named `~` |
| Roots never deduplicated | `providers/claude-code/sessions.ts` | two roots resolving to one place list every session twice; `CLAUDE_CONFIG_DIR="a,a"` is enough to show it |
| A configured root that yields nothing fails silently | `cli.ts` | the message is `No claude-code session files were found.` and names none of the places it looked |

**One candidate was investigated and rejected.** ccusage splits `CODEX_HOME` on
commas, and the first reading of that was that TurnLens contradicts itself by
splitting `CLAUDE_CONFIG_DIR` and not `CODEX_HOME`. Checked against Codex's own
documentation: `CODEX_HOME` names a single directory and no comma form is
documented. The splitting is ccusage's own convenience, because it aggregates
across homes and TurnLens watches one session. Treating the variable as one path
is therefore correct, and the asymmetry between the two providers reflects a real
asymmetry between the two agents rather than an oversight. Adding the feature
would mean shipping behaviour no observed agent has.

Two further findings are scoped rather than fixed here. `~/.codex/
archived_sessions/` is read by ccusage and not by TurnLens; not listing it is
correct for watching and wrong for reporting, so it sits with Plan 5 above. A
project directory's `memory/` subdirectory holds no transcripts, so the
depth-one scan loses nothing by skipping it.

macOS is unmeasured. Every fix above is platform-independent and lands for all
three, but macOS carries the label "expected" until a machine says otherwise.

## Plan 3.7 — Terminal width adaptation (complete)

`docs/superpowers/specs/2026-07-28-terminal-width-adaptation-design.md`

The live table was 174 characters wide and nothing measured the terminal. This
is the fourth defect of one family, and the third reported from Windows: a
session listing wider than its rule, three assertions carrying a Linux
separator, roots deduplicated by spelling, and now a table printed at a width no
window was asked about. Each passed a green suite on Linux because the machine
it was written on happened to satisfy it.

It arrived as one report: the same session read cleanly under GNOME Terminal on
Ubuntu and broke under PowerShell, where the `Tools` heading split into `Too`
and `ls`. That split located the wrap exactly. `Tools` occupies positions 132 to
136, so a break after `Too` is a break at 134, and the diagnosis was that the
window was 134 columns and had wrapped -- not that PowerShell had truncated
anything. Recorded at the time as an inference rather than a measurement.

**What was learned about the platforms.** Terminal width is not a property of
the screen. It is the window's pixel width divided by the character cell's, and
the cell comes from the font and its size; resolution only bounds how wide the
window can be made. The number is read through `ioctl(TIOCGWINSZ)` on Linux and
macOS and `GetConsoleScreenBufferInfo` on Windows, and Node's
`process.stdout.columns` reaches both through libuv, whose Windows path returns
the visible window rather than the console screen buffer -- which matters,
because legacy conhost can have a buffer wider than the window.

Default launch widths are what made this look like a Windows problem: Windows
Terminal opens at 120 columns whatever the screen, while GNOME Terminal and
Terminal.app open at 80 and are habitually maximised. **174 cannot be assumed
anywhere.** A 1366x768 laptop maximised reaches roughly 130 to 150 on any
platform, so the table was broken on all three and only reported from one.

**What ccusage contributed.** It solves the same problem, so what it does is
evidence rather than opinion. Three things were taken: `COLUMNS` resolved before
the detected width, measurement kept in a separate module from layout, and
narrowing conditioned on stdout being a terminal. One was deliberately not
taken. ccusage falls back to a fixed 120 when it can measure nothing; TurnLens
prints the full table instead, because an unmeasurable width means a pipe or a
file, and dropping columns there is silent data loss.

**The design.** One priority order rather than fixed tiers, because sixteen
columns across a 94-character span would have meant three or four separate
tables that could drift apart. Shrink the two flexible columns to their
minimums, drop in priority order until the rest fit, then hand the leftover back
to the prompt. Seven columns are never dropped. Both the full width and the
floor are computed from the column definitions, so adding a column moves them
without anyone remembering to. The width is measured once, before the header,
and frozen: rows receive a layout and never a width, so a window resized
mid-run cannot leave a row misaligned with the header above it.

**Verified on Windows, 28 July 2026, under PowerShell.** A deliberately
half-width window: TurnLens measured 134 columns and said so, showing 13 of 16,
with no heading split and no row wrapped. Maximised, and again in a freshly
opened maximised terminal: the full table and no notice. The 134 is the point.
It was derived from where the break fell before anything was measured, and the
terminal then reported it independently. The instrument agreed with the
diagnosis, which is what separates a fix for the actual cause from a fix for a
plausible one.

Two defects surfaced afterwards, both found by using the thing rather than by
testing it, and both of the same shape: output that was correct by its own
measure and wrong in a real terminal.

The first notice line was 104 characters, so in the 80-column terminal it was
describing, it wrapped -- the defect it was reporting. It wraps at spaces to the
width it names now.

**The last column of the terminal is no longer used.** Fitting the table to
exactly the measured width turned out to be the wrong target. A line that fills
the final column leaves the cursor at the right margin, and terminals record
such a line as continuing into the next one; maximising the window afterwards
re-flows the pair together, which is how a rule was seen running past the
`Duration` column it should have ended at. Reported from Windows after a resize.
Fitting one character short means no line is ever a continuation, whatever a
given terminal believes about margins, and it absorbs the terminals and remote
sessions that report their width off by one. The cost is one character.

Resizing after startup remains outside the design -- columns do not come back,
by decision -- but the rule not surviving a resize was a defect rather than a
consequence of that decision.

Re-measured on Windows after the change: the notice is right in a small window
and the rule ends where it should once the window is maximised. That the
re-flow stopped is also what confirms the diagnosis; the cause was a line
exactly as wide as the terminal, and one reserved column was enough.

### The session listing came back into scope

The design excluded the listing and the summary block, on the grounds that both
fit at 120 and neither was where the reported problem was. That reasoning used
Windows Terminal's default without saying so. Establishing that GNOME Terminal,
Terminal.app and cmd.exe all open at **80** invalidated it for the listing: 100
characters do not fit there, so a default terminal on two of the three platforms
wrapped it. The decision was not revisited when the assumption behind it was
corrected, which is the mistake worth recording.

It matters more than the table. The listing is the first thing TurnLens prints,
and the user has to read it to type a session number in answer to the prompt
below it. A garbled table is irritating; a garbled chooser is an obstacle.

The listing had in fact already been narrowed once for this exact reason -- rows
of 106 and 145 characters under a 100-character rule -- but only the rows were
fixed. The rule's own 100 was never compared against a terminal.

**What is never dropped: the number, the name and the id.** The number is what
the user types, the name is how a session is recognised, and the id is what
matches a CSV filename. That leaves the date as the only droppable column, and
the heading already says the list is most recent first, so recency survives it.

The date does not go at the first character of pressure, which was the first
implementation and was wrong. Dropping it frees 21 characters, so doing that to
recover one left a 100-column terminal printing a 79-column listing with 21
columns wasted. The name gives ground first, and the date leaves only once the
name would fall below 24 characters and stop carrying a recognisable title. In
practice the date survives to 92 columns, and below that the name returns to its
full width -- so the list is at its most readable exactly where space is
tightest.

Verified on both Windows and Ubuntu.

**The notice now prints the override in the reader's own shell syntax**,
`$env:COLUMNS=174` on Windows and `COLUMNS=174` elsewhere, and says plainly that
forcing it will wrap until the window is wide enough. The earlier wording
recommended `COLUMNS` as a way to see more columns, which in a narrow window
reproduces the defect the notice exists to report.

macOS is unmeasured, as ever. Nothing here branches on platform.

## Plan 4 — Packaging and release

`docs/superpowers/plans/2026-07-27-turnlens-packaging-and-release.md`

The work is turning a repository people clone into a package people install.
Nothing about how TurnLens runs changes; what changes is how it reaches anyone.

Today the only route in is `git clone`, `npm install`, `npm run build`,
`node dist/cli.js`. That route works -- verified by cloning the public repository
and following the README verbatim -- but it asks for git, a build step and three
minutes before the first row of output. The destination is `npm install -g
turnlens` or `npx turnlens@latest`.

The package itself is already sound. The packed tarball is 31 files and 37 kB,
and installing that tarball into a scratch prefix produces a working `turnlens`
command. The name is unclaimed on the registry. So this plan is almost entirely
metadata, automation and one irreversible button.

### Nothing is bundled

An earlier bullet here said "bundling", which was wrong and is worth correcting
rather than deleting. A bundler exists to collapse a dependency tree into one
file. There are zero runtime dependencies, so there is no tree, and `tsc` output
ships as it is emitted. The `bin` field is what creates the shell command, and
`files: ["dist"]` is what keeps everything else out.

### Metadata, and one field that is not optional

`version` goes to `0.1.0` and `engines.node` to `>=22.0.0`, both already decided.
The README already states 22.

Four fields are missing: `repository`, `homepage`, `bugs`, `keywords`. Three of
them are presentation -- the npm page and its search. `repository` is not.
Provenance attestation compares it against the repository that published, and a
mismatch fails the publish. It is a functional requirement wearing metadata's
clothes.

Two scripts-and-ignores gaps found while measuring:

- There is no `prepublishOnly`, so `npm publish` today would upload whatever
  happens to be sitting in `dist` -- stale, or absent. CI rebuilds before it
  publishes, so this only bites a publish run by hand, which is exactly what the
  first release will be. It runs the tests and the build.
- `npm pack` drops a `.tgz` in the working directory and `.gitignore` does not
  cover it.

### Distribution: no tokens

Long-lived npm tokens are being retired for publishing, and granular tokens
expire every 90 days. The replacement is trusted publishing: GitHub Actions
proves its identity to npm over OIDC, and no secret is stored in the repository
at all. It has been generally available since July 2025 and emits provenance --
cryptographic proof of which repository, workflow and commit produced the
tarball -- as a side effect.

Three things this constrains, none of them obvious:

- **The publish job cannot run on Node 22.** Node 22 bundles npm 10; trusted
  publishing needs npm 11.5.1 or later. Node 24 and 26 bundle npm 11. The publish
  job pins Node 24 and installs the latest npm regardless, because the bundled
  minor is not something we control.
- **The workflow filename is part of the trust configuration.** npm is told that
  one named file in one named repository may publish. Renaming it later breaks
  publishing with no obvious cause, so the name is chosen once and frozen.
- **Provenance is requested explicitly even though it should be automatic.**
  npm's documentation says the flag is unnecessary under trusted publishing; a
  field report from January 2026 says publishing failed without it. Declaring it
  in `publishConfig` costs nothing if the documentation is right.

### Continuous integration

Two workflows, deliberately separate.

The first runs on every push and pull request and publishes nothing. Its whole
value is the machines the developer does not have: five jobs, ubuntu, macos and
windows on Node 24, plus ubuntu on 22 and 26. A full three-by-three matrix would
add four jobs that answer no question -- the unknown is the platform, not the
minor version, and 22 and 26 are there only to hold the declared floor and the
next Current honest. Actions is free with no minute cap on public repositories.

Windows is the job most likely to fail first, and the code is better prepared
than it looks: every path is composed with `join`, and the tests compare against
`join` results rather than literal separators, so both sides of each assertion
transform identically. That is an argument, not evidence. The job is the
evidence.

### Releasing

The second workflow triggers on a published GitHub Release and nothing else.
Pushing to `main` must never reach the registry: an npm version number is burned
permanently the moment it is used, so publishing has to be an act, not a
side effect.

The ordering trap this creates is worth stating plainly, because it is the most
common way this goes wrong. `package.json` is the only thing npm reads when
deciding what version it is publishing; the git tag is a label. Tagging `v0.1.2`
while the file still says `0.1.0` produces a release page that disagrees with the
registry forever. So the first step of the workflow compares the two and stops
before `npm publish` if they differ, and the documented procedure bumps the file
first and tags the resulting commit.

### The first release is different

Trusted publishing is configured per package, on that package's own page on
npmjs.com -- and an unpublished package has no page. `npm trust github` exists in
npm 11.10 and later and may configure the relationship without one; whether it
works for a package that does not yet exist cannot be established without trying
it. So the plan branches: attempt it, and if it fails, publish `0.1.0` by hand
with a one-time password, then configure trust and let every later version go
through the workflow.

Once the package is up, the README install section is rewritten around
`npx turnlens@latest` -- `@latest` rather than bare `npx`, which can serve a
cached older version.

## Plan 5 — Reporting

Aggregate daily and weekly rollups, JSON and SQLite output, statusline
integration, better historical reconstruction.

**Reporting reads the agent's transcripts, not TurnLens's CSVs.** This is
settled. A CSV lands wherever the command was run, so a report built from CSVs
would first have to find them -- and a user who never ran the watcher would have
nothing to report on. The transcripts, by contrast, are always in the same
places, which is why `ccusage` needs no store of its own. TurnLens already has
the parser and the assembler, so a command in the shape of
`turnlens claude report --daily` re-runs the existing pipeline over every
session and needs no live monitoring at all.

One property is genuinely lost by reconstructing, and the CSV is what keeps it.
Reconstruction prices with today's rates. A recorded row keeps the rate that was
in effect when the turn closed and names the pricing list it used, which is the
deliberate difference from ccusage described under Plan 2. So the two coexist
with different jobs: the report command answers "what have I spent", and the CSV
is an optional ledger for anyone who wants historical figures to stay put when
upstream rates change.

That leaves the store-format question -- whether the CSV stays primary or
becomes an export from something queryable -- to be decided against real
reporting requirements rather than in advance.

**The scope is every session, not one.** Watching selects a single transcript
and follows it; reporting has to find all of them under the agent's roots and
aggregate across them. Half of that exists already -- `listAllSessionsNewestFirst`
does the discovery for both providers -- but nothing above it does. This is not
`importHistory` with the CSV write removed: that function replays one file that
was already chosen, and choosing is the part reporting does differently.

**And "every session" includes the archived ones.** Codex moves a session to
`~/.codex/archived_sessions/` when the user archives it, keeping the same
`rollout-*.jsonl` format. TurnLens does not read that directory. For watching,
not reading it is correct -- an archived session has ended and cannot be
followed, so listing it would offer the user something they cannot choose. For
reporting the same omission is a silent undercount of money actually spent.
Measured on the development machine on 27 July 2026: 5 archived transcripts
against 20 live, so a fifth of that history would be missing from a total. The
directory exists on Windows as well, so this is ordinary Codex behaviour and not
a local artefact.

**Claude Code archives without moving anything, and the marker is in the desktop
client's own store.** Measured on the development machine:
`~/.config/Claude/claude-code-sessions/<a>/<b>/local_<client-id>.json` carries
`isArchived`, and one session flagged `true` there is listed by TurnLens like any
other. Nothing under `~/.claude` marks it, which is why the first look found
nothing.

On Windows the same store sits inside the desktop client's MSIX container, at
`%LocalAppData%\Packages\Claude_<hash>\LocalCache\Roaming\Claude\`.
`anthropics/claude-code#24534` reports it as `%AppData%\Claude\`, which is what
the application sees before Windows redirects it. Any future work that reads this
has to expect both spellings, and cannot resolve the container path without
knowing the package family name.

So an archived Claude Code conversation is still counted, the opposite failure
from Codex: reporting will under-count there and over-count here unless both are
handled deliberately.

**Reading the flag is possible and has a measured cost.** The file is named after
the client's id, not the transcript's — four of five measured filenames matched
no transcript — so the join runs through a `cliSessionId` field inside each file.
That means opening every file in a second directory tree and depending on a
schema nobody documents, which covers only sessions run through that client. For
watching, the answer is no: it would hide a session the user can still write to.
For reporting the calculation differs, because there the flag changes a total
rather than a list, and a total that silently includes archived work is wrong in
a way a list is not. Decide it here, against the real command.

**A correction worth keeping.** The answer moved twice. The first reading was
that no marker existed, and that went into these documents; a web search then
found it reported for Windows; measuring found it on Linux too, with a join key
the report did not mention. Absence of a signal where we looked is not absence of
a signal.

The Codex side is now measured too, and from an unexpected direction. That
machine's `session_index.jsonl` named two sessions while `sessions/` held the
transcript of only one, so the missing one had been archived and moved. The
index outliving the transcript is a usable signal: a name with no file under
`sessions/` is evidence that `archived_sessions/` holds it, without reading that
directory at all.

**Researched before it is designed.** Open questions, none of them answerable
from the code we have:

- Which day a turn belongs to. Transcript timestamps are UTC; a user asking for
  "today" means their own timezone, and a turn closing at 23:50 local time falls
  in a different bucket under each reading.
- What re-running the whole pipeline over every transcript costs. One session
  here is 25 MB and a user may have hundreds. If that is too slow to run on
  every invocation, the answer is a cache, and a cache needs an invalidation
  rule -- which is a design decision, not an optimisation.
- What ccusage's daily and weekly output actually contains and how it buckets,
  so the difference from it is deliberate rather than accidental.
- Whether a report covers all providers at once or one per invocation, which
  decides whether the command reads `turnlens report` or `turnlens claude report`.

## Deferred decisions

- **Per-tool token attribution.** The Python implementation wrote a
  `tool_token_usage_json` column fed by `last_token_usage`, which is the usage of
  the model step that requested a tool, not the tool's own cost. The
  column is not carried over. If it returns it must be named for what it
  measures.
- **`models.dev` as a second pricing source.** Plan 2 shipped LiteLLM only,
  behind an interface that admits a second source. It was not implemented
  because every model Codex and Claude Code emit is already an exact LiteLLM
  key, so a second source would add a merge policy and a second failure mode to
  solve a problem that does not currently exist. ccusage carries three sources
  because it must price anybody's model across fifteen agents.
- **Long-context tier rates** (`_above_200k_tokens`, `_above_272k_tokens`).
  Deliberately unused in v1. A turn's input total is the sum over many requests,
  not one request's context size, so testing that sum against the threshold
  would misprice systematically. The per-request figure exists
  (`last_token_usage.input_tokens`, largest observed 235,115) but summing it
  disagrees with the cumulative delta in 49 of 388 turns, so it is not yet a
  trustworthy basis. Priority, flex, batch and regional variants are out for a
  simpler reason: nothing in a session file says which tier a request used.
- **Subagent cost attribution.** Claude Code writes subagent transcripts to
  `projects/<project>/<session>/subagents/`, not inline in the parent file, so
  Plan 3 records nothing for them. Taking them into scope is not additive: a
  subagent file replays the parent's messages with the same `message.id` but a
  different `requestId`, so the deduplication key would have to change for every
  Claude Code session, including the single-file case that is already verified
  exactly. No session on this machine has ever run a subagent, so there is no
  fixture. Written up in `documentation/future-features.md` section 4.
- **Advisor usage inside `message.usage.iterations`.** The array is present on
  every assistant record, always length one, always mirroring the record's own
  usage -- summing it would double every number. A second type,
  `advisor_message`, is genuinely additional usage under a *different* model.
  Zero instances exist locally, so it is deferred rather than written blind; the
  failure direction while waiting is undercounting, never invention. Written up
  in `documentation/future-features.md` section 3.
- **Store format.** CSV is adequate for one session. Cross-session reporting in
  Plan 5 may want something queryable.
- **Rate-limit windows.** Codex reports `used_percent` and `window_minutes` and
  both are already recorded, but presenting them as a usage indicator needs
  per-provider window modelling: Codex has one weekly window, Claude Code has a
  five-hour and a weekly one. Written up in `documentation/future-features.md`,
  including the four decisions to make before any code is written.
- **`importHistory` is built and tested but not reachable from the CLI.** This
  entry used to say `runWatch` duplicated part of it and that merging the two
  reads was deferred to Plan 2. That was wrong twice over: Plan 2 shipped without
  doing it, and there is no duplicate read to remove. Nothing in `src/` calls
  `importHistory`; `src/cli.ts` calls only `runWatch`, whose one prefix read
  (`readBaseline`) exists to seed the cumulative counter and returns immediately
  for per-event providers. One read, and only for Codex.

  Wiring it to a `--import-history` flag was considered and rejected. Backfilled
  turns would be priced at today's rates, which is exactly the property that
  makes a recorded row worth more than a reconstructed one -- so those rows would
  offer nothing over what Plan 5 can produce from the transcript, in exchange for
  a flag, a wait and a second scan.

  It stays because it is the batch path through the pipeline, and because the
  arithmetic lock is built on it: the turn counts taken by hand, the tool-call
  attribution, the byte-identical guarantee and the snapshot pricing tests all
  drive it. Plan 5 will generalise it, keeping the traversal and dropping the
  CSV write. Until then it is deliberately internal, not forgotten.

### Display width is still counted in code units

**Deferred, deliberately, with no date on it.** `fit` in `ui/live-table.ts` pads
with `padEnd` and `padStart`, and both count UTF-16 code units. A terminal
allocates cells, and the two are equal only for the Latin range -- Turkish
included, which is why nothing in daily use trips it.

They part company in both directions. `日本語で書いてください` is 11 code units and
22 cells, so the column is padded as though it were 11 wide and drawn 11 cells
too wide, pushing the row past the window. A family emoji is 8 code units and 2
cells, so the same column comes out too narrow. Either way the row stops lining
up with its header, which is the defect this plan set out to remove, arriving by
a different road.

Closing it needs a `displayWidth` in `core/text.ts` -- East Asian Wide and
Fullwidth counted as 2, combining marks as 0, the rest as 1 -- and `fit`
padding by that instead. It belongs in `text.ts` for the reason the cutting
fix did: `truncate` is the one place that decides how much text fits, and the
table, the listing, the banner and the summary block all reach it through the
same path.

Two things argue for leaving it. TurnLens does not claim CJK support today and
is not planned to, so the failing input is one no user of it is expected to
type. And terminals disagree with each other about emoji width -- the same
emoji is one cell in some and two in others -- so the fix would be exact for
CJK and approximate for emoji however carefully it is written. A half-built
Unicode table that is wrong in a new way is worse than an honest note.

The related defect that did have to be fixed is recorded above: cutting a
character in half is data corruption rather than a display flaw, and it reached
the CSV. `truncate` and `truncateEnd` now cut on grapheme boundaries via
`Intl.Segmenter`, which is built into Node.
